# Ingestion windows and permanent capture history

Daily and manual ingestion use actual execution time from the application clock. The chosen week is for browsing and report coverage, and cannot move ingestion's run time into the future or back to midnight. Each provider starts a run record before watermark lookup. Lookup failures are recorded for that provider; remaining providers continue when persistence is available.

Exa intentionally searches an overlapping three-day publication window to accommodate delayed indexing and day-only publication dates. Other public pull providers use the last successful start, with a bounded lookback. Slack and Notion are outside the current provider scope. Ahrefs and Semrush retain per-run metric snapshots.

Capture storage uses one transaction and a unique version registry keyed by Workspace, provider, canonical URL and exact SHA-256 content fingerprint. An unchanged page reuses its existing capture across all stored history, repeated results in a batch, concurrent writes and callback reprocessing. A changed body creates a new capture. Reuse leaves original IDs, capture dates and payloads unchanged. Every search result and callback/pull observation retains provenance and a capture reference, including raw snapshots. Runs report newly created captures, reused captures and observations separately. Observations also make reused evidence available in the current Weekly Report period; newsletter research remains automatically reusable by Weekly Reports.

Canonicalization normalizes the URL scheme and host, removes known tracking parameters/fragments, and sorts query pairs. It preserves path and query-value case and correctly escapes query delimiters. URL lineage does not establish content equivalence.

Normalized identical content and known formatting/boilerplate variants receive an incrementally computed evidence group. Material changes stay separate. Fuzzy similarity only creates a bounded review suggestion during insertion; reads never compare all captures. A complete representative and earliest underlying publication date are derived group metadata, and never overwrite historical capture dates or publications. Latest explicit Keep/Junk judgments apply to equivalent content; retraction is a separate eligibility state. Confirm/separate decisions and judgment history remain stored.

Legacy captures are not deleted. Follow the snapshot/backfill process in [newsletter operations](newsletter.md) before enabling workers on existing data. The registry chooses a reusable legacy version while retaining all original copies and citations.
