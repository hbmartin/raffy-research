# PRD: Weekly CEO Market Intelligence Digest

## 1. Product summary

This product generates a weekly, interactive market-intelligence report for **small, early-stage B2B SaaS CEOs**, especially **pre-seed, pre-revenue founders** operating in a narrow industry subcategory.

The report helps the CEO understand:

1. **What market narratives and industry conversations are emerging.**
2. **Which competitors or adjacent companies appear to be gaining momentum.**
3. **What evidence may inform future marketing and GTM allocation decisions.**

The product does **not** give advice or make recommendations in V1. It surfaces evidence, observations, questions, contradictions, and relevant source material so the CEO can decide what matters.

The core artifact is a **frozen weekly web report** backed by permanently stored source data. The report is grouped topically, supports drilldown into evidence, and links to both internally stored sources and original external sources.

---

# 2. Target user

## Primary user

**Small early-stage B2B SaaS CEO**

Initial target profile:

* Pre-seed
* Pre-revenue
* Narrow subcategory focus
* No dedicated market intelligence analyst
* Likely founder-led GTM
* Needs to monitor market movement without manually reading dozens of channels

## Secondary users

V1 is primarily CEO-facing. Secondary users may exist later, but they are not first-class V1 users.

Potential future users:

* Chief of staff
* Founder / cofounder
* Marketing lead
* GTM operator
* Product lead
* Analyst
* Investor / board observer

## V1 audience assumption

The report is **internal-facing only**. No public sharing, customer-facing claims, or external communications are generated by the system.

---

# 3. Product promise

## Core promise

Every Monday morning, the CEO receives a frozen interactive report showing what changed, what people are talking about, what competitors are doing, which questions are emerging, where contradictions exist, and what evidence supports those observations.

## The report should feel like

A lightweight **analyst brief plus evidence workspace**, not a generic news digest and not a prescriptive strategy memo.

It should help the CEO answer:

* “What industry conversations are becoming more common?”
* “What narratives are competitors leaning into?”
* “What questions are buyers or users asking?”
* “What signals might affect how I think about marketing focus?”
* “Are external market signals contradicting our internal assumptions?”
* “Which people or companies are showing possible lead-like intent?”
* “Which sources should I inspect myself?”

---

# 4. V1 goals

## Goal 1: Generate a useful weekly market digest

The product should automatically generate and publish a weekly report every Monday morning.

The report should contain:

* 3-bullet executive summary
* What looks most interesting
* Contradictions / assumptions to revisit
* Emergent topic clusters
* Competitor watch
* Market questions
* Possible leads
* Social / product feedback
* Source library

Sections should appear only when there is new evidence. Empty sections should show a small collapsed line: **“No new evidence this week.”**

## Goal 2: Preserve source provenance

Every evidence item in the report must include source IDs and link back to internally stored source records.

Each cited item should support drilldown:

```text
Topic
→ Evidence
→ Source excerpt
→ Stored source side panel
→ Original external source
```

## Goal 3: Store all raw source data permanently

All provider payloads, search results, webhook callbacks, scraped content, source metadata, diffs, and internal notes should be stored permanently in Postgres.

V1 treats storage as cheap.

## Goal 4: Keep V1 implementation simple

V1 should avoid complex architecture unless necessary.

Specifically, V1 should defer:

* embeddings
* semantic search
* follow-up Q&A
* deterministic deduplication
* confidence scoring
* source weighting
* structured signal taxonomy
* lead enrichment
* human review queues
* full source archive UI
* feedback-driven ranking
* task creation
* agentic execution

---

# 5. Non-goals for V1

V1 does **not**:

* Recommend marketing actions
* Tell the CEO how to allocate budget
* Generate outreach copy
* Enrich leads
* Create tasks
* Assign owners
* Trigger workflows
* Rewrite or regenerate successful weekly reports
* Provide confidence labels or confidence scores
* Use embeddings
* Offer follow-up Q&A
* Provide a full archive browser for all captured sources
* Perform deterministic deduplication
* Require human review before publishing
* Support self-serve onboarding

# 6. Key definitions

These terms should be used consistently in engineering, prompts, database schema, and UI.

## Workspace

A customer/company environment.

A workspace contains:

* company profile
* configured keywords
* configured competitors
* configured social accounts
* configured providers
* configured Slack / Notion sources
* stored source records
* weekly reports
* feedback events

## Provider

A third-party or internal integration that fetches or delivers data.

Examples:

* Apify
* Exa
* Awario
* Trigify
* ForumScout
* Visualping
* Distill.io
* SEMrush
* Ahrefs
* Slack
* Notion

Important distinction: **the provider is not the source.**

Example:

* Provider: Apify
* Source: LinkedIn post
* Provider: Visualping
* Source: competitor homepage change event
* Provider: Slack
* Source: Slack thread

## Source

The original thing being referenced.

Examples:

* LinkedIn post
* LinkedIn comment thread
* Reddit thread
* Hacker News discussion
* forum post
* competitor homepage
* competitor pricing page
* competitor changelog
* blog post
* search result
* Ahrefs keyword report
* SEMrush domain report
* Visualping page-change event
* Distill.io page-change event
* Slack thread
* Notion page

## Source record

The internal Postgres representation of a captured source.

A source record contains:

* core structured columns
* source/provider identifiers
* captured text
* metadata
* raw provider payload
* links
* optional diff data
* JSONB payload for everything provider-specific

## Signal

In V1, a signal is a loose concept, not a strict schema.

A signal can mean:

* a mention
* a question
* a competitor change
* a social post
* a forum thread
* a lead-like event
* an internal assumption
* a contradiction
* a search result
* a webpage diff
* a possible evidence candidate

V1 does **not** require structured signal taxonomy. V2 may introduce typed signals.

## Evidence item

A report-ready piece of support for an observation.

Examples:

* source excerpt
* quoted post
* summarized forum question
* added/removed webpage diff
* search result snippet
* internal Slack excerpt
* Notion note excerpt
* provider metric summary

Every evidence item must include one or more source IDs.

## Observation

An LLM-generated, evidence-backed statement in the report.

Example:

> “Several buyer conversations this week focused on implementation complexity rather than model quality.”

Observations should be grounded in evidence. They should not make recommendations.

## Report artifact

A frozen weekly report object stored in Postgres and rendered as an interactive web page.

The report contains generated text, section structure, selected evidence items, source references, and metadata.

## Feedback event

A recorded user action.

Examples:

* useful
* not useful
* more like this
* less like this
* flag bad synthesis
* open source
* copy excerpt
* add suggested competitor to watchlist

In V1, feedback is recorded but does not affect ranking, regeneration, or report content.

# 7. V1 product behavior

## Weekly cycle

Default schedule:

```text
Coverage window: Monday–Sunday
Generation time: Monday morning
Timezone: company timezone
Default timezone: America/Los_Angeles
```

Every Monday morning, the system automatically generates and immediately publishes the weekly report.

There is no human review step.

## Frozen reports

Once successfully published, a weekly report does not change.

A successful report cannot be regenerated.

Exception:

* If this week’s report failed, it may be regenerated.

## Failed generation

If weekly generation fails:

* record the failure
* store failure metadata
* alert an internal Slack channel
* do not silently retry
* do not overwrite the prior report
* allow regeneration only because the report failed

A sparse report is acceptable when evidence is sparse. A failed report is different from a sparse report.

## Sparse reports

If little new evidence exists, the report should still publish.

Sections with no evidence should display:

> No new evidence this week.

This should be collapsed by default.

# 8. Data source strategy

## V1-critical providers

The architecture should support all listed providers in V1, but the system must continue working when any individual provider is not configured.

| Provider   | V1 role                                                     |
| ---------- | ----------------------------------------------------------- |
| Apify      | Mandatory LinkedIn monitoring; custom scraping where useful |
| Exa        | Daily time-bounded web search over configured keywords      |
| Awario     | Social listening                                            |
| Trigify    | LinkedIn/social buying intent or lead-like triggers         |
| ForumScout | Reddit/forum/customer-question monitoring                   |
| Visualping | Competitor webpage change detection                         |
| Distill.io | Competitor webpage change detection                         |
| SEMrush    | SEO, keyword, and competitive search visibility             |
| Ahrefs     | SEO, keyword, backlink, and domain momentum                 |
| Slack      | Internal thread/note evidence                               |
| Notion     | Internal page/note evidence                                 |

## Provider optionality

Each provider should be configurable per workspace.

If a provider is not configured:

* skip its ingestion jobs
* do not block report generation
* do not show provider-specific errors to the CEO unless the report itself fails

## Overlapping providers

Visualping and Distill.io overlap. V1 should support both or either behind a generic webpage-monitoring integration pattern.

SEMrush and Ahrefs overlap. V1 should support both or either behind a generic SEO-provider pattern.

This allows customers/operators to stay on cheaper provider tiers by splitting coverage.

# 9. Configuration model

V1 setup is operator-assisted. It does not require self-serve onboarding.

However, configuration must live in the database, not in application code.

## Workspace configuration

Required:

* company name
* company timezone
* narrow subcategory
* company description / context

Optional:

* company website
* current positioning
* known ICP
* known market assumptions
* notes about current GTM focus

## Keywords

V1 keyword configuration is intentionally simple.

Required fields:

```text
workspace_id
keyword_string
active
created_at
updated_at
```

Keywords are plain strings in V1.

V1 should support time-bounded search over configured keywords.

Future architecture should allow richer keyword types, such as:

* exact phrase
* broad match
* negative keywords
* category tag
* competitor tag
* persona tag
* priority
* source-specific usage
* geography
* language

These are V2+.

## Social accounts

V1 requires only one of:

```text
profile_url
```

or:

```text
platform
username
```

No complex social account taxonomy is required in V1.

## Competitors

V1 requires only:

```text
competitor_name
domain
```

Suggested competitors should have state:

```text
suggested
accepted
ignored
```

Accepted competitors become part of the watchlist.

## Internal notes

V1 may configure:

* one or more Slack channels
* one or more Notion pages

All configured Slack/Notion sources are allowed and may be used as evidence.

Configured internal notes are not restricted to keyword-matching content in V1.

# 10. Ingestion requirements

## Ingestion principles

V1 ingestion should be simple and durable.

The system should:

* store raw provider payloads
* store source and provider as distinct concepts
* preserve as much metadata as possible
* store raw/extracted content whenever available
* avoid deterministic deduplication
* not discard low-confidence or duplicate-looking sources
* support callbacks and scheduled ingestion
* continue operating with partially configured providers

## Service callbacks

The system should accept callbacks/webhooks from configured providers.

Callback examples:

* Apify actor run completed
* Visualping change detected
* Distill.io change detected
* Awario mention detected
* Trigify lead trigger detected
* ForumScout mention/question detected
* Slack event
* Notion update
* manual upload or manual source insertion

Each callback should create durable raw records.

Provider cadence is determined by the provider. Web search is the exception: it runs daily.

## Daily web search

Daily web search should:

* run against configured keyword strings
* be time-bounded to recent results
* store search results in a dedicated table
* store maximum metadata
* optionally fetch/store the linked page as a source record when practical

Search result records are not the same as fetched source records.

## Webpage monitoring

For Visualping and Distill.io events, V1 should store and display text diff data.

The report UI should show:

* added text
* removed text

V1 does not need:

* screenshot diff
* inline visual diff
* advanced semantic diff
* LLM-generated diff confidence

## Internal notes ingestion

Slack and Notion ingestion should:

* ingest only configured sources
* store raw content and metadata
* make internal notes eligible as report evidence
* treat internal evidence equally with external evidence

V1 does not need granular Slack/Notion permissions.

The assumption is that configured sources are intentionally allowed for the CEO-facing internal report.

# 11. Storage requirements

## Storage approach

Postgres is the system of record.

Major tables should use:

```text
core structured columns
+ jsonb payload / metadata column
```

The JSONB field should capture everything provider-specific or not yet normalized.

Storage should be treated as cheap.

## No deterministic deduplication

V1 does not dedupe deterministically.

Do not block source insertion based on:

* URL
* canonical URL
* provider source ID
* content hash
* semantic similarity

The LLM is responsible for deduping at the weekly synthesis/report level.

It is acceptable for the database to contain duplicate or near-duplicate source records.

# 12. Weekly report generation pipeline

## V1 pipeline

```text
1. Collect stored source records for current report period.
2. Collect workspace config.
3. Collect configured keywords, competitors, social accounts, and company context.
4. For trend/change sections only, collect prior report summaries.
5. Assemble LLM context.
6. Generate section/topic report data.
7. Generate executive summary and “what looks most interesting.”
8. Generate trend labels where evidence supports them.
9. Produce schema-valid report JSON.
10. Store report in Postgres.
11. Publish dynamic report page.
```

## Prior reports usage

Prior reports should only be used for distinct trend/change prompts.

They should not contaminate current-week evidence.

Current-week observations should cite current-week sources.

Prior reports may help generate labels such as:

```text
New this week
Rising
Stable
Declining
```

But prior reports should not become evidence for current claims.

## Context-size assumption

V1 assumes data volume is small enough to fit within a single model context window.

If context size becomes too large, V1 may fail the generation run, record the failure, and alert Slack.

V2 should solve scaling with summarization, chunking, retrieval, embeddings, or map-reduce pipelines.

## Generation retries

V1 should not perform full job-level retries.

For malformed JSON, the system may perform a bounded schema repair/formatting step within the same generation attempt.

If output remains invalid, mark the report as failed and alert Slack.

## Schema validation

Before publishing, report data must conform to the V1 report JSON schema.

V1 does not need to validate that every emitted source ID exists, but every evidence item must include source IDs in the expected field.

# 13. Report data shape

The top-level report shape should be stored in `weekly_reports.report_data`.

Suggested shape:

```json
{
  "workspace_id": "uuid",
  "report_id": "uuid",
  "period_start": "2026-06-01",
  "period_end": "2026-06-07",
  "generated_at": "2026-06-08T08:00:00-07:00",
  "timezone": "America/Los_Angeles",
  "title": "Weekly Market Digest",
  "executive_summary": {
    "bullets": []
  },
  "what_looks_most_interesting": [],
  "contradictions": [],
  "topic_clusters": [],
  "competitor_watch": [],
  "market_questions": [],
  "possible_leads": [],
  "social_product_feedback": [],
  "source_library": []
}
```

## Executive summary

The executive summary should contain exactly 3 bullets.

Emphasis should be on:

1. Most important market narrative / industry conversation
2. Most notable competitor or ecosystem movement
3. Most important GTM or marketing question raised by the evidence

The summary should not recommend actions.

## What looks most interesting

This is the “operator-like” section.

It should call out the items most likely to matter to the CEO, but without recommendations.

The LLM may decide what is interesting using qualitative judgment.

Signals of interest may include:

* newness
* repeated language
* relevance to configured keywords
* relevance to tracked competitors
* contradiction with internal assumptions
* strong social engagement
* possible marketing/GTM implications
* possible lead-like signals

Allowed behavior:

* surface
* highlight
* frame
* ask questions
* point to evidence

Disallowed behavior:

* recommend
* prescribe
* allocate budget
* create tasks
* say “you should”

## Contradictions / assumptions to revisit

This section should appear near the top of the report, after the executive summary and what-looks-interesting section.

Reason: contradictions are high-value for CEOs.

Examples:

* Internal notes assume buyers care about speed, while external conversations emphasize compliance.
* Competitor messaging shifts toward a narrative the company has not discussed internally.
* Social feedback indicates a pain point missing from internal positioning.
* Internal GTM assumptions conflict with observed market questions.

The report should label contradictions explicitly.

## Topic clusters

Topic clusters are LLM-generated but must be grounded in evidence.

The report uses a hybrid structure:

* fixed report sections
* emergent LLM-generated topic clusters

Fixed sections only show when there is new evidence.

Each topic cluster should include:

```json
{
  "id": "topic_1",
  "title": "string",
  "summary": "string",
  "observation": "string",
  "why_this_may_matter": "string",
  "labels": {
    "newness": "new_this_week | existing",
    "trend": "rising | stable | declining | unknown"
  },
  "representative_evidence": [],
  "all_evidence": [],
  "related_competitors": [],
  "related_keywords": [],
  "related_internal_sources": []
}
```

No confidence labels or confidence scores in V1.

## Competitor watch

Competitors should appear in two places:

1. Inside topic clusters where relevant
2. In a short Competitor Watch section

The Competitor Watch section should not become a large dashboard.

It should focus on meaningful source-backed changes, such as:

* positioning changes
* page changes
* product launches
* social/account activity
* SEO/search visibility changes
* repeated mentions
* new competitor suggestions

## Suggested competitors

Suggested competitors should include:

* name
* domain if available
* why suggested
* source evidence
* similarity to workspace/company
* mention velocity if available
* overlap with tracked keywords
* action button: add to watchlist

A suggested competitor should normally require at least two independent signals unless manually added.

When the CEO clicks **Add to watchlist**, the competitor state becomes:

```text
accepted
```

## Market questions

Market Questions should mean actual observed questions from the market.

Examples:

* forum questions
* Reddit questions
* LinkedIn questions
* search-result questions
* public buyer questions
* category/customer questions

Decision prompts generated by the LLM should be separate from Market Questions.

Market Questions are evidence. Decision prompts are interpretation.

## Possible leads

V1 lead detection should be the simplest possible implementation.

A possible lead is any person or company appearing in LinkedIn, social, forum, or scraped content whose post/comment contains a configured keyword or competitor name and expresses one of:

* question
* complaint
* search for alternatives
* buying intent
* relevant pain
* category exploration

No enrichment in V1.

Possible lead card should include:

* person/company if available
* source excerpt
* why this may be relevant
* matched keyword or competitor
* source links
* useful / not useful
* more like this / less like this

No outreach angle in V1.

## Social / product feedback

For pre-revenue companies, direct product feedback may be sparse.

This section may include:

* direct mentions of the company/product
* competitor product feedback
* category-level feedback
* pain points from target users
* social reactions to relevant narratives

Items should be clearly labeled so category feedback is not mistaken for direct product feedback.

## Source library

The report source library should include:

* sources cited in the report
* relevant-but-unused sources selected by the LLM

It should not include every captured source in the workspace.

The full source archive UI is V2.

Source library should be grouped by topic cluster.

Filters by source type or provider are useful but not mandatory in V1.

# 14. Evidence and citation requirements

## Evidence item structure

Suggested evidence shape:

```json
{
  "id": "evidence_1",
  "source_ids": ["uuid"],
  "excerpt": "string",
  "source_title": "string",
  "source_type": "string",
  "provider_name": "string",
  "external_url": "string",
  "internal_source_url": "string",
  "notes": "string"
}
```

Every evidence item must include source IDs.

V1 does not need strict source ID validation before publishing.

## Citation display

Collapsed topic card:

* show 1–3 representative evidence items

Expanded topic card:

* show all evidence items selected by the LLM for that topic

Source library:

* show cited sources
* show relevant-but-unused sources

## Internal and external citations

The report should provide both:

* internal stored source link
* original external source link

The internal stored source link is the durable citation.

The original external URL is useful context.

## Provider display

CEO-facing evidence should prioritize the original source.

Provider should be secondary metadata.

Example:

```text
LinkedIn post · captured via Apify
```

Not:

```text
Apify result
```

# 17. Feedback requirements

## V1 behavior

Feedback should be recorded only.

Feedback should not:

* change current report ordering
* change current report content
* regenerate a report
* modify future prompts
* affect source ranking
* affect source ingestion
* change provider configuration

Exception:

* Add suggested competitor to watchlist should update competitor state.

```text
less_like_this
flag_bad_synthesis
open_source
copy_excerpt
add_competitor_to_watchlist
```

Each event should capture:

* workspace ID
* report ID

* target type
* target ID

* timestamp
* JSONB payload

# 18. LLM behavior requirements

## Core behavior

The LLM should generate:

* executive summary
* what looks most interesting
* topic clusters
* competitor watch
* market questions
* possible leads
* social/product feedback
* contradictions
* source library associations

## No advice or recommendations

V1 report should not recommend actions.

The product can surface:

* evidence
* observations
* questions
* decision prompts
* possible implications
* follow-up research areas

The product should not say:

* increase spend
* reduce spend
* launch campaign
* prioritize this channel
* email these leads
* build this feature
* change positioning

No separate formal language style guide is required in V1, but the generation prompt should include the no-recommendations constraint.

## Deduplication

The LLM is responsible for deduping at synthesis time.

It should avoid repeating the same observation if multiple providers captured the same source or event.

## Trend labels

V1 supports:

```text
New this week
Rising
Stable
Declining
```

These labels are generated by the LLM only when evidence supports them.

Prior reports may be used only for distinct trend/change prompts.

Prior reports should not be cited as evidence for current-week observations.

## Confidence

No confidence labels in V1.

No confidence scores in V1.

Confidence diagnostics are V2.

# 19. Failure and edge-case behavior

## Provider not configured

Expected behavior:

* skip provider
* do not block generation
* do not show irrelevant missing-provider warnings to CEO

## Provider callback malformed

Expected behavior:

* store raw payload if possible
* mark normalization failed if needed
* do not block other ingestion
* log error metadata

## Duplicate sources

Expected behavior:

* store duplicates
* do not dedupe at write time
* let LLM collapse repeated evidence in report generation

## No evidence for a section

Expected behavior:

* show small collapsed “No new evidence this week” row

## Little evidence overall

Expected behavior:

* publish sparse report

## Report generation failure

Expected behavior:

* status = failed
* store failure reason
* alert Slack
* allow regeneration because this week failed
* do not silently retry

## External URL disappears

Expected behavior:

* internal source record remains available
* original URL may fail externally
* internal citation remains durable
